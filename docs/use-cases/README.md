# Use cases

Each use case is written for two audiences at once. The **business view** covers the problem,
objectives, stakeholders and outcomes. The **technical view** covers the requirements, workflow,
components, agents, failure handling, security, observability, acceptance criteria and tests.

## Handbook use cases (existing, preserved)

The original repository's projects, documented in the same structure in condensed form. They are
learning implementations: no authentication, and local storage only. Each row notes what a
production version would need. Sentinel shows that path for an agentic system.

### UC-H1: Todo API exposed as MCP tools (`handbook/001-fastapi-mcp-todo`)

| Field | Detail |
|---|---|
| Business problem | Let an AI assistant manage a task list through tools, not screen-scraping |
| Actors | User, MCP client (assistant), API |
| Functional | CRUD on todos (`/todos`), validation with Pydantic, SQLite persistence; `/mcp` exposes `list_todos`, `get_todo`, `create_todo`, `update_todo`, `delete_todo` |
| Input / output | JSON `TodoCreate`/`TodoUpdate` → `Todo`; 404 for unknown ids |
| Workflow | MCP `tools/call` → fastapi-mcp → internal HTTP call → route → SQLite |
| Failure handling | 404 / 422; transactional connection helper with rollback |
| Security gaps | No auth on API or MCP; free-tier Render disk is ephemeral |
| Acceptance | Verified after the restructure: CRUD round trip and MCP `initialize` return 200 |
| To productionise | API keys/OAuth for MCP (as in Sentinel), PostgreSQL, migrations, rate limiting |

### UC-H2: Multimodal daily meal plan (`handbook/004-project-daily-meal-plan`)

| Field | Detail |
|---|---|
| Business problem | Personalised meal plans with images and narrated instructions |
| Functional | Prompt-engineered plan (text) → DALL-E images per meal → TTS audio per meal |
| AI responsibilities | Generation only; no tools |
| Failure handling | Notebook-level; no retries |
| Security | Keys were hard-coded in an earlier version (redacted; see SECURITY.md) |
| To productionise | Structured output schema, content safety filter, cost metering, caching |

### UC-H3: Question answering over private documents (`handbook/005-langchain-and-rag`)

| Field | Detail |
|---|---|
| Business problem | Answer questions grounded in PDF, DOCX and TXT documents |
| Functional | Load → chunk (recursive splitter) → embed (OpenAI) → Chroma/Pinecone → retrieve → answer with chat memory; Streamlit UI |
| Non-functional | Chunk size and k are tunable; embedding cost is shown in the UI |
| Failure handling | Unsupported formats rejected |
| To productionise | Document-level access control, evaluation set (faithfulness and answer relevance), re-indexing pipeline |

### UC-H4: Talk to an image / rename images (`handbook/006-gemini-api`)

| Field | Detail |
|---|---|
| Business problem | Ask questions about photos; generate descriptive file names |
| Functional | Gemini vision prompts; Streamlit upload UI; batch renaming |
| To productionise | File type and size validation, PII review of images, rate limiting |

### UC-H5: Research agent (`handbook/012-capstone-research-agent`)

| Field | Detail |
|---|---|
| Business problem | Produce a cited research report on a topic |
| Functional | LangGraph "oracle" chooses tools (ArXiv fetch, SerpAPI web search, Pinecone RAG over papers) until it calls `final_answer`; formatted report |
| AI responsibilities | The LLM selects tools (autonomous loop), unlike Sentinel's fixed pipeline |
| Failure handling | Iteration cap on the loop |
| To productionise | Tool timeouts and retries, citation verification, tracing (LangSmith/OTel), cost caps |

**Design contrast.** UC-H5 lets the LLM choose tools in a loop, which suits open-ended research.
Sentinel uses a fixed pipeline with deterministic ranking, because incident response needs results
that are reproducible, auditable and safe. Pick the pattern by the cost of a wrong action.
